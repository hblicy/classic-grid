# PopDEX Agent 草稿状态修复设计

## 目标

修复 Dashboard 页面中两个会丢失 Agent 私钥的状态管理问题：重复生成会覆盖尚未保存的草稿；清理或撤销旧配置会误删与旧配置无关的新草稿。

本次只调整 `public/popdex-agent.js` 的浏览器状态流和对应回归测试，不修改后端 API、链上交易格式、Agent 授权规则或页面结构。

## 状态边界

页面同时维护两类独立状态：

- 已配置状态来自后端 `getAgentStatus()`，代表 `.env` 中已保存的 Agent。
- 草稿状态由 `generatedPrivateKey`、`generatedAgentAddress`、`connectedMainAccount` 和 `authorizationVerified` 组成，只存在于当前页面内存。

清理后端配置不得隐式清理草稿。只有草稿已经保存，或用户明确同意覆盖未授权草稿时，页面才可以丢弃草稿私钥。

## 重复生成

`generateAgent()` 在创建新钱包前检查当前草稿：

- 没有草稿时直接生成。
- 草稿已完成链上授权回验时拒绝生成，并提示先保存当前 Agent；不得提供会覆盖该私钥的确认路径。
- 草稿尚未完成链上授权时，弹窗明确说明现有私钥将被永久覆盖；用户确认后才生成，取消则保持所有草稿状态不变。

生成按钮在事件包装器结束后继续可用，因为未授权草稿仍允许用户明确确认后重新生成；安全约束由 `generateAgent()` 在覆盖发生前执行。

## 清理与撤销

`clearLocalAgent()` 只负责验证并删除后端已配置 Agent。后端清理成功后：

- 页面没有草稿时，清空草稿相关控件并显示已清理信息。
- 页面存在草稿时，保留私钥、地址、主账户和授权回验状态，不调用全量重置函数；刷新后仍显示草稿地址及可用的复制、授权或保存按钮。

`revokeAgent()` 继续复用 `clearLocalAgent(true)`，因此链上撤销后的自动清理遵守同一规则，不会误删另一个页面草稿。

## 错误处理

- 用户取消覆盖属于正常退出，不显示错误，也不改变状态。
- 已授权草稿触发重复生成时抛出可识别错误，由现有 `run()` 包装器显示。
- 后端清理失败时保留全部草稿和已配置状态，由原错误路径向用户展示失败。

## 测试策略

使用 Node `vm` 执行真实 `public/popdex-agent.js`，提供最小 DOM、钱包、fetch 和 ethers 测试替身，通过按钮点击走实际事件处理路径。测试按红绿顺序加入：

1. 已授权未保存草稿再次生成时，钱包创建次数和页面私钥均不变化，并显示先保存提示。
2. 未授权草稿再次生成时，取消确认保留原草稿；确认后才替换。
3. 旧配置已撤销且页面存在新草稿时，手动清理只调用后端 clear，保留草稿私钥和按钮状态。
4. 撤销旧配置后的自动清理同样保留既有草稿。

最后运行目标 UI 测试、完整 `npm test`、`git diff --check`；TypeScript 全量检查若仍有既有错误，精确区分本次变更文件。

## 验收标准

- 已授权未保存的 Agent 私钥不能被重复生成覆盖。
- 未授权草稿只能在用户明确确认后被替换。
- 清理或撤销已配置 Agent 不会删除另一个内存草稿。
- 没有草稿时，清理后的原有控件重置行为保持不变。
- 新增状态机回归测试和现有测试全部通过。
