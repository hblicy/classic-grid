# 订单归属持久化设计

## 背景

重心化保护只允许程序撤销当前进程下单回执中确认过的订单。现有实现把这些订单 ID 仅保存在内存 `ownedOrderIds` 中；进程重启后集合为空，交易所原有挂单全部变成未知订单，程序因此保护暂停。人工撤掉全部挂单虽然可以重新启动网格，但撤单和重新铺单都会产生大量链上交易与 gas 成本。

## 目标

- 正常停止和重启后恢复机器人订单归属，不要求撤单重铺。
- 保持现有安全边界：未明确记录的订单仍然是未知订单，禁止自动撤销。
- 为部署前已经存在的机器人挂单提供一次性、显式确认的接管流程。
- 状态损坏或写盘失败时明确暂停或终止，不吞掉错误。
- 不在状态文件中保存私钥、API Key 或其他凭据。

## 非目标

- 不自动推断任意未知订单属于机器人。
- 不改变网格策略、订单价格、下单量、重心化阈值或交易所 API。
- 不自动撤销人工订单。
- 不解决 Decibel gas 定价或 Gas Station 配置问题。

## 方案选择

采用“显式接管 + 订单 ID 持久化”。不采用按价格自动认领，因为仅凭价格和数量无法证明订单归属；也不通过关闭重心化保护绕过检查。

## 状态文件

新增 `data/order-ownership.json`，作为订单归属的唯一持久化来源。文件不进入 Git，结构带固定版本号：

```json
{
  "version": 1,
  "venues": {
    "decibel": {
      "market": "BTC",
      "grid": {
        "anchorMid": 63314.2,
        "gridCount": 65,
        "spacing": 89.9136568,
        "sizeBase": 0.0040822,
        "mode": "neutral"
      },
      "orders": [
        {
          "id": "exchange-order-id",
          "side": "buy",
          "price": 62000,
          "size": 0.0040822,
          "level": 18
        }
      ],
      "updatedAt": "2026-08-14T00:00:00.000Z"
    }
  }
}
```

加载时必须校验版本、交易所、市场、有限数值、正数价格和数量，以及同一交易所内订单 ID 唯一性。文件不存在表示尚未建立归属；JSON 损坏或结构非法则抛错并阻止实盘启动。

保存时先在同目录写临时文件，再原子替换正式文件。临时文件名包含当前进程 ID，避免同名冲突。写入失败必须向上传播，不能继续交易。

## 一次性接管命令

新增 npm 命令：

```bash
npm run adopt-orders -- --venues=risex,decibel --market=BTC
```

默认行为只读：连接指定交易所、读取当前挂单、从 `data/status.json` 读取软恢复锚点并展示每所订单数量、方向、价格范围、下单量范围和预期网格数量。它不调用 `apply`、`cancelAll` 或任何写交易方法，也不写归属文件。

只有显式确认全部当前挂单均属于机器人时才写文件：

```bash
npm run adopt-orders -- --venues=risex,decibel --market=BTC --confirm-all-bot-orders
```

写入前必须满足：

- 操作者已经停止主机器人进程。
- 每个交易所都连接成功并取得实时挂单。
- `data/status.json` 中存在同交易所、同市场的有效锚点与网格参数。
- 所有订单 ID 非空且唯一，价格和数量为正数。
- 所有订单能唯一映射到保存网格的某个价格档；允许同一档存在重复订单，但预览必须醒目标出，接管后仍由现有网格逻辑处理。

任一交易所验证失败时整次接管不写文件，避免只接管一半。命令不会用环境变量偷偷开启自动接管，确认参数不会被长期保留在 `.env`。

## 启动和运行时数据流

1. `runLoop` 在连接交易所前加载并严格校验归属文件。
2. 软恢复锚点优先使用归属文件中的网格指纹；仅在该交易所没有归属记录时回退到旧的 `data/status.json`。
3. 建立当前网格后，将归属文件中的市场、锚点、格数、间距、下单量和模式与当前配置比较。任何不一致都会暂停该交易所，不会撤单或新增订单。
4. 获取交易所实时挂单后，按“交易所 + 市场 + 精确订单 ID”与持久化记录求交集，恢复 `ownedOrderIds` 和 `active`。
5. 持久化记录存在但实时挂单已不存在的订单，视为已成交或已撤，在本轮计划完成后从文件清除。
6. 实时挂单存在但持久化记录不存在的订单，继续触发现有未知订单保护暂停。
7. 每次交易所明确返回成功下单 ID 后，先把完整订单信息写入归属文件，再允许下一轮写操作。
8. 已确认撤单不立即猜测结果；下一次实时快照确认订单消失后再从归属文件删除。

## 失败处理和可观测性

- 文件缺失且交易所有挂单：保护暂停，提示运行接管命令。
- 文件损坏、版本不支持或重复 ID：实盘启动失败并输出具体文件与字段错误。
- 网格指纹不一致：对应交易所暂停，日志打印保存值和当前值，不自动覆盖。
- 下单成功但归属写盘失败：对应交易所立即进入暂停状态，日志明确说明订单已上链但未持久化，并输出订单 ID；不得继续新增或撤销。
- 清理过期 ID 时写盘失败：保持内存中的旧归属并暂停写操作，避免状态继续分叉。
- 正常启动日志打印每所“加载记录数、实时匹配数、已清理数、未知数”，不打印密钥或 Token。

## 代码边界

- 新建 `src/orderOwnership.ts`：状态类型、校验、加载、原子保存、增删与实时对账，独立于交易所 SDK。
- 新建 `src/cli/adopt-orders.ts`：参数解析、只读预览、显式确认和全量原子接管。
- 修改 `src/loop.ts`：加载归属、恢复运行时集合、网格指纹检查、下单后持久化和快照清理。
- 修改 `package.json`：增加 `adopt-orders` 命令和对应测试入口。
- 新建 `test/orderOwnership.test.ts`：纯临时目录测试状态文件与对账逻辑。
- 新建 `test/adoptOrders.test.ts`：用只读假执行器验证预览、确认和全有或全无写入，不连接真实交易所。
- 更新 `README.md`：记录首次接管、正常重启和故障恢复步骤。

## 测试要求

- 文件不存在返回空状态；损坏、错误版本、重复 ID 和非法数值均失败。
- 保存再加载保持订单与网格指纹，且不会残留半写正式文件。
- 对账只恢复精确 ID；清理消失订单；返回额外未知订单。
- 已持久化订单重启后不会触发未知订单暂停。
- 额外一个未记录订单仍会暂停，且不会产生撤单或下单意图。
- 网格指纹变化会暂停，不修改归属文件。
- 下单成功后的订单在进入下一轮前已经写盘；写盘失败会暂停。
- 接管命令无确认参数时不写文件；确认后写入全部指定交易所；任一验证失败时零写入。

所有自动化测试使用临时目录和假交易所，不读取 `.env`，不发送链上交易。

## 部署流程

1. 合并并部署新代码，但保持机器人停止。
2. 备份 `data/status.json` 和现有账本。
3. 运行接管预览，核对 RISEx 与 Decibel 数量和价格范围。
4. 使用确认参数写入 `data/order-ownership.json`。
5. 正常启动机器人，确认日志中的实时匹配数等于交易所当前挂单数且未知数为零。
6. 后续正常重启只停止和启动程序，不再撤销现有挂单。
