# PopDEX Agent 回验恢复与服务端并发保护设计

## 背景

当前 Agent 生命周期仍有两个失败边界：

1. 浏览器钱包返回授权交易哈希后，如果等待回执或后端回验失败，页面会保留草稿私钥并禁止重复生成/授权，但也会禁用保存，用户无法在不重发交易的前提下完成流程。
2. 页面级互斥只覆盖单个标签页。服务端 `clear()` 在异步链上查询前读取旧私钥，查询期间另一标签页或直接 API 可以保存新私钥；旧 `clear()` 随后可能清除新私钥。

本次只修复这两个问题，不修改公开 API、链上 calldata、页面结构、依赖或既有 TypeScript 基线错误。

## 方案选择

### 浏览器端恢复

考虑过三种方案：

1. 新增“重试回验”按钮：语义清楚，但需要修改页面结构和增加一套状态转换。
2. 让“刷新链上状态”兼顾草稿回验：不增加按钮，但会混淆“已保存配置状态”和“未保存草稿状态”。
3. 复用现有“验证并保存”按钮：钱包返回交易哈希后允许点击保存，由现有 `/api/popdex/agent/save` 再次执行精确链上回验；回验成功才写入，失败则保留草稿供稍后重试。

采用方案 3。按钮本身已经叫“验证并保存”，后端 `save()` 也已经在写盘前校验 Agent 地址、delegator、有效期和非全局权限，因此不增加新的安全信任边界，也不会重发授权交易。

### 服务端并发

考虑过三种方案：

1. 只依赖浏览器互斥：无法覆盖多标签页和直接 API 调用，不采用。
2. 只在 `clear()` 写入前比较私钥：能阻止已知覆盖，但其他身份写操作仍可交错。
3. 在 `PopdexAgentService` 内串行化 `save()` 与 `clear()`，并在 `clear()` 最终写入前再次确认当前私钥仍等于已完成撤销回验的私钥。

采用方案 3。FIFO 队列保护同一 Dashboard 进程内的身份写操作；最终一致性检查作为防御层，在状态已变化时返回明确冲突错误，不清除任何配置。

## 浏览器状态流

1. 生成 Agent 后，`authorizationSubmitted=false`、`authorizationVerified=false`。
2. 钱包返回交易哈希时立即：
   - 设置 `authorizationSubmitted=true`；
   - 保存本次连接的主账户到内存；
   - 保留 Agent 私钥和地址。
3. 首次回验成功时设置 `authorizationVerified=true`；失败时仍保留 submitted 状态。
4. 只要存在私钥、主账户且授权交易已提交或已回验，启用“验证并保存”。
5. 点击保存时始终调用现有 save API：
   - 链上授权仍未可见或 RPC 失败：显示错误，保留全部草稿状态，按钮可再次点击；
   - 链上授权有效且写盘成功：清除浏览器内存草稿并刷新已保存状态。
6. 生成与授权在 submitted 状态继续保持禁用，确保重试保存不会重复发送授权交易。

## 服务端串行化与一致性检查

`PopdexAgentService` 增加实例级 FIFO 身份写队列：

- `save()` 和 `clear()` 的权限检查、链上读取和写盘都在队列临界区内执行；
- 排队后重新执行 `assertMutationAllowed()`，避免等待期间 PopDEX 恢复运行后仍继续写配置；
- `clear()` 记录本次回验的私钥，在写盘前比较 `processEnv.POPDEX_AGENT_PRIVATE_KEY`；若不同，抛出“Agent 配置已变化，拒绝清除”的业务错误；
- 队列必须在成功和失败路径都释放，单次 RPC 或写盘失败不能阻塞后续操作。

该队列解决同一服务实例上的多标签页/API 并发；跨进程同时编辑同一 `.env` 仍不在本次范围内，部署应继续保持单一 Dashboard 写入者。

## 错误处理

- 授权交易已提交后的回验/保存失败不得清除或覆盖草稿私钥。
- 服务端发现配置变化时明确拒绝清除，不静默成功。
- 非预期 RPC 和写盘错误继续向调用方传播；队列只负责顺序，不吞异常。
- 不记录或返回 Agent 私钥。

## 测试

### 浏览器回归测试

- 首次 `/verify` 失败后，生成和授权仍禁用，但保存按钮启用；
- 随后点击保存会调用 save API，成功后清除草稿；
- 整个恢复过程只发送一次 `eth_sendTransaction`；
- 保存重试失败时草稿仍保留，按钮仍可再次使用。

### 服务回归测试

- 延迟旧 Agent 的 `clear()` 链上查询，同时发起新 Agent `save()`；验证写操作按顺序完成，最终保留新私钥；
- `clear()` 回验期间若当前私钥被其他路径改变，最终一致性检查拒绝清除并保留新值；
- 队列中的一次失败不会阻塞后续保存或清除。
