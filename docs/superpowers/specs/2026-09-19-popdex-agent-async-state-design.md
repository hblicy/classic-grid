# PopDEX Agent 异步状态保护设计

## 目标

关闭两个仍可能丢失 Agent 私钥的异步状态缺口：链上交易已提交但回验失败后仍允许覆盖草稿，以及多个 Agent 生命周期操作可并发交错。

本次只修改 `public/popdex-agent.js` 和对应浏览器状态机测试，不修改后端 API、链上 calldata、授权规则或页面结构。

## 根因

页面当前只用 `authorizationVerified` 区分普通草稿与不可丢弃草稿。钱包返回交易哈希后，如果等待回执或后端回验失败，该值仍为 `false`，但链上交易可能已经成功或仍可能成功，重新生成会覆盖唯一私钥。

此外，`run()` 只禁用当前点击的按钮。授权、保存、撤销或清理中的 `await` 会把执行权交回页面，其他按钮可以启动第二个生命周期操作并修改同一组全局状态。

## 授权提交状态

新增浏览器内存布尔值 `authorizationSubmitted`：

- 新草稿生成时为 `false`。
- `eth_sendTransaction` 返回交易哈希后立即变为 `true`，早于等待回执和服务端回验。
- 交易哈希一旦存在，即使等待回执超时或授权回验失败，也保持 `true`；页面不能再生成新草稿或重复授权。
- 授权回验成功后，同时保持 `authorizationSubmitted=true` 并设置 `authorizationVerified=true`，允许保存。
- 成功保存或明确重置无草稿状态时恢复为 `false`。

这是保守的 fail-closed 行为。只有钱包在返回交易哈希前拒绝请求时，当前未授权草稿仍可经确认后覆盖。页面重新加载仍会丢失内存草稿，这是现有产品边界，不在本次增加持久化。

`sendAndConfirm()` 接收一个交易已提交回调，在拿到哈希后、等待回执前调用。这样调用方可以在任何后续异步失败前记录不可丢弃状态，而撤销交易无需改变现有状态。

## 单一操作锁

新增 `operationInProgress`，所有 Agent 按钮都通过同一个 `run()` 包装器进入操作：

- 如果已有操作进行中，新的操作直接退出并显示“另一项 Agent 操作正在进行中”。
- 操作开始时统一禁用生成、复制、授权、保存、刷新、撤销和清理按钮。
- 操作结束时统一根据草稿、授权提交、授权回验和后端配置状态恢复按钮。

统一按钮同步函数替代 `run()` 中只恢复当前按钮的分支。生成按钮在 `authorizationSubmitted` 或 `authorizationVerified` 为真时保持禁用；授权按钮在交易已提交后保持禁用；保存按钮只有授权回验成功时可用。

该锁只覆盖页面内 Agent 生命周期操作，不改变 Dashboard 其他暂停、恢复、撤单或网格操作。

## 错误处理

- 钱包在返回交易哈希前拒绝：不设置 `authorizationSubmitted`，保留现有草稿，可再次授权或确认覆盖。
- 已返回哈希后等待失败：保留私钥并锁定生成/重复授权，错误中保留交易哈希上下文。
- 交易确认但后端回验失败：保留私钥并锁定生成/重复授权，允许用户稍后刷新或重新加载后人工核对。
- 并发点击：第二项操作不调用钱包或 API，不修改任何草稿/配置状态。

## 测试策略

扩展现有 Node VM 页面测试框架，使钱包回执、授权回验和保存 API 可以由测试延迟或失败：

1. 钱包交易确认、`/verify` 失败后，再点击生成不会创建第二个钱包，原私钥保持不变。
2. 钱包已返回哈希但回执仍等待时，再点击生成不会创建第二个钱包。
3. 保存 API 等待时点击清理，不会发出 clear 请求；保存结束后按钮状态恢复。
4. 钱包在返回交易哈希前拒绝时，草稿仍可重新授权或经明确确认覆盖。
5. 现有生成、授权、保存、撤销与清理测试继续通过。

每项生产代码改动前先运行对应新测试并确认因当前缺陷失败，再实施最小修复。

## 验收标准

- 交易哈希已经返回后，任何回执或回验结果都不能使页面覆盖该 Agent 私钥。
- 任意时刻最多执行一个 Agent 生命周期操作。
- 并发点击不会产生第二个钱包请求、链上请求或冲突 API 写入。
- 钱包发送前失败不会错误地永久锁住普通草稿。
- 全部状态机回归测试和现有完整测试通过。
